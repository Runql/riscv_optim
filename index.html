1. Objective & Progress

Objective

Investigate whether and how the LC3plus codec can be optimized for RISC-V, similar to the existing ARM optimizations. This includes:

  • Required tools for Linux-based testing and profiling
  • CI integration requirements
  • Optimization for both fx (fixed-point) and fl (floating-point) code paths

Scope

The current setup and optimization work are based on RV64 Linux with RVV (rv64gcv, lp64d). RV32 has not been covered so far. It can be evaluated later if a 32-bit RISC-V target becomes relevant.

4. Profiling

Profiling identifies which functions consume the most execution time (hotspots). Only these hotspot functions need to be optimized with RVV intrinsics — not the entire codebase.

Spike offers two profiling modes, both of which map program-counter (PC) addresses to functions:

  • -g (aggregated per-address counts) — recommended, used in CI
  • -l (full instruction trace) — optional, for short manual debugging only

4.1  -g : Aggregated Hotspot Profiling (recommended, used in CI)

spike --isa=rv64gcv -g pk ./NBCenc_riscv_static [arguments] 2> histogram.txt
Flag Meaning Required?
-g Aggregate execution count per PC address For profiling
2> histogram.txt Save histogram to file Optional (otherwise prints to screen)

The raw -g output only lists program-counter addresses with their execution counts — not yet human-readable:

PC             count
0x10100        12,000
0x10104        12,000
0x10108        12,000
0x1010c        12,000
0x10200         8,000
0x10204         8,000
...

To map these addresses back to function names, disassemble the binary:

riscv64-unknown-linux-gnu-objdump -d ./NBCenc_riscv_static > disassembly.txt

Combining both sources maps each hot address to its function:

spike -g:                        →    objdump disassembly:

0x10100: 12,000 hits                  0000000000010100 <processMdctShaping_fx>:
0x10104: 12,000 hits             →       10100:  vsetvli t0,a0,e32,m4
0x10108: 12,000 hits                     10104:  vle32.v v0,(a1)
0x1010c: 12,000 hits                     10108:  vsmul.vx v0,v0,a2
                                         1010c:  vse32.v v0,(a1)
→ total: 48,000 hits (45%)

0x10200:  8,000 hits                  0000000000010200 <fft_complex>:
0x10204:  8,000 hits             →       10200:  addi sp,sp,-64
                                         10204:  sd ra,56(sp)

→ total: 16,000 hits (15%)

Based on profiling results:

  • Functions with highest instruction count → optimize with RVV intrinsics
  • Functions with low count → keep as pure C (not worth the effort)

To automate this mapping, use the following script profile_report.py:


"""Combine spike -g histogram with objdump disassemblyto produce a per-function hotspot report.Usage:    python3 profile_report.py histogram.txt disassembly.txt    python3 profile_report.py histogram.txt disassembly.txt > hotspots.txt"""
import sys
import re
from collections import defaultdict

def parse_disassembly(path):
    """Return dict: pc (int) -> function name"""    pc_to_func = {}
    current_func = "<unknown>"
    with open(path) as f:
        for line in f:
            # function label: 0000000000010100 <processMdctShaping_fx>:            m = re.match(r'^([0-9a-f]+)\s+<([^>]+)>:', line)
            if m:
                current_func = m.group(2)
                continue
            # instruction line: 10100:  ...            m = re.match(r'^\s+([0-9a-f]+):', line)
            if m:
                pc_to_func[int(m.group(1), 16)] = current_func
    return pc_to_func

def parse_histogram(path):
    """Return dict: pc (int) -> count"""    pc_to_count = {}
    with open(path) as f:
        for line in f:
            parts = line.strip().split()
            if len(parts) == 2:
                pc    = int(parts[0], 16)
                count = int(parts[1])
                pc_to_count[pc] = count
    return pc_to_count

def main():
    histogram_file   = sys.argv[1]   # histogram.txt
    disassembly_file = sys.argv[2]   # disassembly.txt

    pc_to_func  = parse_disassembly(disassembly_file)
    pc_to_count = parse_histogram(histogram_file)

    # aggregate per function    func_counts = defaultdict(int)
    for pc, count in pc_to_count.items():
        func = pc_to_func.get(pc, "<unknown>")
        func_counts[func] += count

    total = sum(func_counts.values())

    # print sorted report    print(f"\n{'Function':<50} {'Count':>12} {'%':>8}")
    print("-" * 73)
    print(f"{'TOTAL':<50} {total:>12,} {'100.00%':>8}")
    print("-" * 73 + "\n")
    for func, count in sorted(func_counts.items(), key=lambda x: -x[1]):
        pct = 100.0 * count / total if total else 0
        print(f"{func:<50} {count:>12,} {pct:>7.2f}%")

if __name__ == "__main__":
    main()

Run: print to terminal

Save to file (useful for CI artefacts or sharing)

6.1  How RVV Intrinsics Work

Instead of processing one element per instruction, RVV intrinsics let a single instruction operate on a vector of elements simultaneously, making loops significantly faster on data-parallel workloads like DSP.

RVV intrinsics follow a consistent naming pattern:


    __riscv  _operation  _type/config
    │         │          │
    │         │          └── type/config: element width + LMUL(register grouping)
    │         └───────────── operation (load, mul, shift...)
    └─────────────────────── common prefix for all RVV intrinsics

Example: processMdctShaping_fx in mdct_shaping_fx.c, which is called by Enc_Lc3_Channel:

C
processMdctShaping_fx 		RVV Implementation
mdct_shaping_func1		 

/* Scalar: inner loop processes one element per iteration */
Word16 j = 0;
FOR (i = 0; i < fdns_npts; i++)
{
    FOR (; j < bands_offset[i + 1]; j++)
    {
        x[j] = L_shl(Mpy_32_16(x[j], scf[i]), scf_exp[i]);
    }
}


/* Vector: inner loop processes up to `vl` elements per iteration */
for (int i = 0; i < fdns_npts; i++) {
    int32_t scf_s = (int32_t)scf[i] << 16;
    int     shift = scf_exp[i];
    size_t  n     = bands_offset[i+1] - bands_offset[i];
    int32_t *p    = &x[bands_offset[i]];

    if (shift >= 0) {
        for (size_t vl; n > 0; n -= vl, p += vl) {
            vl         = __riscv_vsetvl_e32m4(n);
            vint32m4_t v = __riscv_vle32_v_i32m4(p, vl);
            v          = __riscv_vsmul_vx_i32m4(v, scf_s, __RISCV_VXRM_RNU, vl);
            v          = __riscv_vsll_vx_i32m4(v, shift, vl);
            __riscv_vse32_v_i32m4(p, v, vl);
        }
    } 
    else {
        for (size_t vl; n > 0; n -= vl, p += vl) {
            vl           = __riscv_vsetvl_e32m4(n);
            vint32m4_t v = __riscv_vle32_v_i32m4(p, vl);
            v            = __riscv_vsmul_vx_i32m4(v, scf_s, __RISCV_VXRM_RNU, vl);
            v            = __riscv_vsra_vx_i32m4(v, -shift, vl);
            __riscv_vse32_v_i32m4(p, v, vl);
        }
    }
}

load x[j] __riscv_vle32_v_i32m4 Load vl elements into a vector register

Vector length (vsetvl):

RVV does not have a fixed vector width. Each iteration, __riscv_vsetvl_e32m4(n) asks the hardware how many of the remaining n elements it can process, and returns that count as vl. The maximum is determined by:

vl ≤ (VLEN × LMUL) / SEW
Parameter Meaning This example
VLEN Physical vector register width (fixed by the hardware) 128 bit
LMUL Register grouping (set by code, here m4) 4
SEW Element width (set by code, here e32) 32 bit

So here vl ≤ (128 × 4) / 32 = 16. If fewer than 16 elements remain, vsetvl returns the remaining count instead — which is why no separate tail loop is needed. Because VLEN differs between chips (128 / 256 / 512...), the same code automatically processes more elements per iteration on wider hardware.

6.2  Code Patterns Suitable for RVV Optimization

Not all code benefits from RVV. The key requirement is data parallelism —the same operation applied to many elements independently

Good candidates:

  1. Large loop

    Same operation on every element:

    for (int i = 0; i < N; i++) {
    out[i] = a[i] * b[i] + c[i];
}

    ⬇ RVV

    for (size_t vl; N > 0; N -= vl, a += vl, b += vl, c += vl, out += vl) {
    // Load vl elements per iteration    vl              = __riscv_vsetvl_e32m4(N);
    vfloat32m4_t va = __riscv_vle32_v_f32m4(a, vl);
    vfloat32m4_t vb = __riscv_vle32_v_f32m4(b, vl);
    vfloat32m4_t vc = __riscv_vle32_v_f32m4(c, vl);

    // a*b + c    vfloat32m4_t vr = __riscv_vfmadd_vv_f32m4(va, vb, vc, vl);

     // Store vr in out    __riscv_vse32_v_f32m4(out, vr, vl);
}

  1. Accumulation loop

    for (int i = 0; i < N; i++) {
    acc += a[i] * b[i]; 
}

    ⬇ RVV

    
// Get count of lanes: vl_max = (VLEN × LMUL) / SEWsize_t       vl_max = __riscv_vsetvlmax_e32m4();

// Initial vsum[0]=0, vsum[1]=0, vsum[2]=0 ...... (The length of vsum is vl_max)vfloat32m4_t vsum   = __riscv_vfmv_v_f_f32m4(0.0f, vl_max);

for (size_t vl; N > 0; N -= vl, a += vl, b += vl) {
    // Load vl elements per iteration    vl              = __riscv_vsetvl_e32m4(N);
    vfloat32m4_t va = __riscv_vle32_v_f32m4(a, vl);
    vfloat32m4_t vb = __riscv_vle32_v_f32m4(b, vl);

    // vfmacc: vsum[i] += va[i] × vb[i] parallelly for all vl lanes    // After the loop: vsum[i] = a[i]*b[i] + a[i+vl_max]*b[i+vl_max] + ... (stride = vl_max)    vsum            = __riscv_vfmacc_vv_f32m4(vsum, va, vb, vl);
}

/* Reduce all lanes → single scalar */
// vfredusum: res[0] = initial_value + vsum[0] + vsum[1] + ...// initial_value = __riscv_vfmv_v_f_f32m1()vfloat32m1_t res = __riscv_vfredusum_vs_f32m4_f32m1(vsum, __riscv_vfmv_v_f_f32m1(0.0f, 1), vl_max);

// Extract res[0] → scalar floatfloat acc = __riscv_vfmv_f_s_f32m1_f32(res);

  1. Nested loop (vectorize the inner loop)

    Inner loop is independent:

    for (int i = 0; i < M; i++) {
    for (int j = 0; j < N; j++) {
        out[i][j] = a[i][j] * b[i][j];
    }
}

    ⬇ RVV

    float  *ap = a[i];
    float  *bp = b[i];
    float  *op = out[i];
    size_t  n  = N;
    for (size_t vl; n > 0; n -= vl, ap += vl, bp += vl, op += vl) {
        // Load vl elements per iteration        vl              = __riscv_vsetvl_e32m4(n);
        vfloat32m4_t va = __riscv_vle32_v_f32m4(ap, vl);
        vfloat32m4_t vb = __riscv_vle32_v_f32m4(bp, vl);

        // vr = va * vb        vfloat32m4_t vr = __riscv_vfmul_vv_f32m4(va, vb, vl); 

        // Store vr in out        __riscv_vse32_v_f32m4(op, vr, vl); 
    }
}

6.3  Vector Masking

Standard RVV applies the same operation to all lanes. When a loop contains a per-element condition, different lanes must take different paths — masking controls which lanes participate:

for (int i = 0; i < N; i++) {
    if (a[i] > 0)
        out[i] = a[i] * 2;
    else
        out[i] = 0;
}

A mask is a boolean vector — one bit per lane:


a:    [  3,  -1,   0,  -2,   7,   0,  -3,   4 ]
mask: [  1,   0,   0,   0,   1,   0,   0,   1 ]
         ↑                   ↑              ↑
      participate        participate    participate

RVV Code Example:

for (size_t vl; N > 0; N -= vl, a += vl, out += vl) {
    vl = __riscv_vsetvl_e32m4(N);

    // Load a[i]    vint32m4_t va = __riscv_vle32_v_i32m4(a, vl);

    // Generate mask: mask[i] = (a[i] > 0)    vbool8_t mask = __riscv_vmsgt_vx_i32m4_b8(va, 0, vl);

    // Set all lanes to 0 first    vint32m4_t vr = __riscv_vmv_v_x_i32m4(0, vl);

    // Only lanes where mask=1 execute a[i]*2; others stay 0    vr = __riscv_vmul_vx_i32m4_m(mask, vr, va, 2, vl);

    __riscv_vse32_v_i32m4(out, vr, vl);
}

7. Further Optimization Directions

Beyond manual RVV intrinsics, three additional approaches can improve performance with minimal or no code changes:

7.1  Auto-vectorization

-march=rv64gcv already enables auto-vectorization — no additional changes are needed.

See , then switch to the Floating-point (fl) tab:

Comparing _baseline (no vectorization) vs _autovec (auto-vectorization only), total instructions dropped from 2,520,368,717 to 2,049,303,518 (−18.7%), without writing any RVV code.

In the gem5 simulator, auto-vectorization can cause the simulation to fail because the compiler generates instructions that are not supported by the simulated target hardware.

So when doing manual RVV optimization, I leave it disabled by default.



7.2  Bit-Manipulation Extensions (Zba/Zbb/Zbs)

Appending _zba_zbb_zbs to -march enables dedicated bit-manipulation instructions:

-march=rv64gcv_zba_zbb_zbs

and profiling with:

spike --isa=rv64gcv_zba_zbb_zbs -g pk ./NBCenc_riscv_static <arguments>

For example, Zbb provides clz (count leading zeros), which the compiler can use to accelerate LC3plus norm functions such as norm_l / norm_s — these functions internally call __builtin_clz() and are called frequently in fixed-point arithmetic.

Without Zbb, __builtin_clz() falls back to __clzdi2 — a multi-instruction software routine from libgcc. With Zbb enabled, the compiler uses single hardware clz/clzw instruction instead.

7.3  Scalar Operator Mapping

Similar to the existing LC3_operators_arm.h, LC3_operators_riscv.h is created to map LC3plus scalar operators to RISC-V-specific instructions.

For example, Mpy_32_32_0 originally computes:

z = L_shr( L_add( Mpy_32_32( x, y ), 1 ), 1 );

On RISC-V, this is replaced with:

int64_t p  = (int64_t)x * (int64_t)y;
Word32  mh = (Word32)( p >> 32 );

#ifdef ENABLE_HR_MODEUWord32 ml = (UWord32)p;
mh += (Word32)(ml >> 31);
#endif
return mh;

This maps to a 64-bit signed multiply followed by extraction of the high 32-bit word.

With ENABLE_HR_MODE, bit 31 of the low word is added to the high word to preserve the HR-mode rounding behavior, matching the existing ARM optimized implementation.



7.4  LTO + PGO

LTO (Link-Time Optimization): add -flto to the compiler flags.

  • LC3plus has many small DSP helper functions — L_shl, Mpy_32_16, norm_l, etc. — defined across different .c files and called thousands of times per frame.
    • Without LTO, the compiler sees only one file at a time, so it cannot inline these helpers — every call becomes a call instruction.
  • -flto makes all files visible at link time, allowing these helpers to be inlined directly at the call site instead of going through a function call.

PGO (Profile-Guided Optimization): the compiler collects a real execution profile and uses it to guide branch prediction and inlining decisions — typically 5–15% gain:


# Step 1: add -fprofile-generate → compile an instrumented binary that records which branches and functions are executed at runtimeriscv64-unknown-linux-gnu-gcc ... -fprofile-generate -o NBCenc_riscv_pgo

# Step 2: run with real input → the instrumented binary writes *.gcda profile data filesqemu-riscv64 -L /opt/riscv/sysroot ./NBCenc_riscv_pgo input.wav output.wav 128000

# Step 3: add -fprofile-use → recompile using the collected *.gcda datariscv64-unknown-linux-gnu-gcc ... -fprofile-use -o NBCenc_riscv_optimized

LTO and PGO are typically applied in a later integration phase, once the code is functionally verified and hotspots have been identified via profiling.

8.3  MCPS using gem5

MCPS (Million Cycles Per Second) measures how many processor cycles the codec consumes per second of audio — the primary indicator of real-world runtime performance and how much CPU headroom remains after optimization.

Cycle-based measurement is not available in Spike or QEMU:

  • Spike — returns dynamic instruction counts, not hardware cycles
  • QEMU — wall-clock time is unreliable due to vector emulation overhead

gem5 is therefore used instead. It is a timing-aware architectural simulator: it models the CPU pipeline, cache hierarchy and memory system, and produces a cycle count for a given, configured hardware model.

⚠️ Note: gem5's cycle count is specific to the simulated CPU/cache/memory model — it is not the cycle count of a specific physical RISC-V chip. It is mainly useful to compare the scalar baseline against the RVV-optimized
